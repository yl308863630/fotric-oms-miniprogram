# 合同生成与取值校验说明（指派 → 模板合同生成 → 指派订单生成）

本文档说明当前程序中「指派、模板合同生成、指派订单生成」的流程及合同取值来源，便于与参考版本（如 0301）对照校验。

## 一、流程概览

1. **指派**：采购/指派 Tab 中点击某订单的「指派」，打开指派弹窗，填写/选择：交付方(乙方)、出货方、扣率、采购价、甲方抬头、支付方式、合同模板、乙方业务员等。
2. **保存到订单**：点击「生成合同」时，先 **PUT** 更新该订单（把弹窗里的 deliveryParty、shippingParty、deductionRate、deliveryPartyPurchasePrice 等写回订单），再 **POST** 生成合同。
3. **合同生成**：后端 `POST /api/contracts/generate-from-order/{salesOrderId}` 调用 `createContractFromSalesOrder`，用**当前库里的订单**（即刚 PUT 后的数据）生成合同并带甲方章，状态为「待签署」。

## 二、合同取值来源（与 0301 可对照项）

| 合同字段 / 占位符 | 当前程序取值来源 | 可能问题点 |
|------------------|------------------|------------|
| **甲方** partyA / partyAName / ${甲方} | 优先 `salesOrder.getOperationEntityTitle()`，为空则 `resolvePartyATitle(salesOrder)`（创建人公司 → 默认飞础科） | 若订单未维护代运营主体，会走兜底逻辑 |
| **乙方** partyB / partyBName / ${乙方} | `salesOrder.getDeliveryParty()`；详情（地址/开户行/税号/电话）来自 PartnerInfo.findByTitle(deliveryParty) | 若 PUT 时 deliveryParty 被 logistics[0] 覆盖则错（已修复） |
| **结算方** settlementParty | 仅工业电商：`salesOrder.getTopLevelCustomerName()`，其他为空 | 非工业电商合同不显示结算方 |
| 产品/金额/日期等 | contract 从 salesOrder 对应字段赋值（model、quantity、taxIncludedPrice、deliveryDate 等） | 依赖订单主表与 orderDetails 已更新 |
| 合同模板 | 前端 `assignForm.templateUrl`，支持下拉选择或输入模板名，生成前 `resolveTemplateUrl` 解析为实际 URL | 若用户输入模板名但未失焦就点「生成合同」，可能用到空需在生成前再次用输入框值解析 |

## 三、已修复的问题（与“合同生成和取值”相关）

1. **PUT 时 deliveryParty 被覆盖**  
   - **现象**：指派弹窗里填的「交付方」在生成合同时未生效，合同乙方变成 logistics[0] 里的旧值。  
   - **原因**：`SalesOrderController` 的 PUT 里 `syncOrderFromFirstLogistics` 无条件用 logistics[0] 的 deliveryParty/shippingParty/deliveryDate 覆盖请求体顶层同名字段。  
   - **修复**：  
     - 后端：顶层已显式传入且非空的 deliveryParty、shippingParty、deliveryDate 时，不再用 logistics[0] 覆盖。  
     - 前端：生成合同前 PUT 时，顺带把 `updateBody.logistics[0].deliveryParty` / `shippingParty` 设为与顶层一致，保证物流与主表一致。

2. **乙方名称为空**  
   - 生成文档前会调用 `ensureContractPartyBFromSalesOrder(contract, salesOrder)`：若合同乙方名称为空，用订单 deliveryParty 回填名称，并从 PartnerInfo 补全地址/开户行/税号/电话。  
   - 乙方仍依赖「PUT 后订单的 deliveryParty 正确」，故修复 1 是前提。

## 四、与 0301 对照时可重点校验的环节

- **指派弹窗**：交付方、甲方抬头、合同模板、乙方业务员是否在点击「生成合同」前都写回表单（含失焦写入），并随 PUT 提交。  
- **PUT /api/sales-orders/:id**：请求体顶层 `deliveryParty`、`shippingParty` 是否被保留（当前已保证不被 logistics[0] 覆盖）。  
- **POST /api/contracts/generate-from-order/:id**：是否在 PUT 之后调用；后端是否用 `salesOrderRepository.findById` 取**最新**订单（当前是，且无二次缓存）。  
- **合同实体**：partyA/partyAName 是否来自订单代运营主体或兜底；partyB/partyBName 是否来自 `salesOrder.getDeliveryParty()`；乙方详情是否来自 PartnerInfo（当前是）。  
- **文档占位符**：DocumentService.buildPlaceholders 中 ${甲方}、${乙方}、${settlementParty} 等是否与 contract 的 partyAName、partyBName、settlementPartyName 一致（当前一致）。  
- **模板名解析**：若 0301 在生成前用「当前输入框的模板名」解析 URL，可对比当前 `resolveTemplateUrl(assignForm.templateUrl)` 及失焦写入时机，必要时在点击「生成合同」时用输入框当前值再解析一次。

## 五、关键代码位置（当前项目）

- 指派 + 生成合同前端：`oms-frontend/src/views/purchase/PurchaseList.vue`（`handleAssignSalesOrder`、`generateContract`、`updateBody` 与 logistics[0] 同步）。  
- 订单 PUT 与 logistics 回填：`oms-backend/.../SalesOrderController.java`（`update`、`syncOrderFromFirstLogistics`）。  
- 合同创建与取值：`oms-backend/.../ContractService.java`（`createContractFromSalesOrder`、甲方/乙方/结算方赋值、`ensureContractPartyBFromSalesOrder`）。  
- 占位符与印章：`oms-backend/.../DocumentService.java`（`buildPlaceholders`、`replacePlaceholdersWithPartySeal`）。

若 0301 中「指派、模板合同生成、指派订单生成」的合同生成和取值与上述任一环节不一致，可按上表逐项对比定位差异。
