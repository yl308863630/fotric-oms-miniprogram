# 验证码 IP 白名单设计

## 目标

用于 OpenClaw、受控办公网络或固定出口 IP 场景下，允许特定来源在登录时跳过验证码。

注意：
- 白名单是安全策略，不是普通用户属性
- 推荐后端判断，不推荐前端跳过

## 推荐设计

### 方案结论

推荐做成：
- **后端统一判断**
- **数据库可维护**
- **admin 可在后台调整**
- **保留配置文件兜底白名单**

不推荐：
- 把白名单直接挂在普通 `users` 表字段里
- 只做前端 `skipCaptcha()`

## 为什么不要直接塞进“用户信息”字段

IP 白名单本质是：
- 全局安全控制
- 与登录入口耦合
- 需要独立审计

它不是某个用户的业务资料，所以更适合：
- 放在独立表
- 通过 admin 的安全管理入口维护

## 最合适的后台入口

推荐两种做法：

### 做法 A：用户管理下新增子页

例如：
- `用户管理 -> 登录安全`
- 页面中维护“验证码 IP 白名单”

优点：
- admin 容易找到
- 不增加太多一级菜单

### 做法 B：独立“安全设置”页

例如：
- `系统设置 -> 登录安全`

优点：
- 语义最清晰
- 方便以后扩展失败次数锁定、登录审计、白名单账号范围

### 当前项目建议

结合现有菜单结构，建议先做：
- `用户管理` 下新增一个子页面，例如 `登录安全`

但数据和接口要独立，不与用户 CRUD 混用。

## 数据模型建议

表名建议：
- `captcha_ip_allowlist`

字段建议：
- `id`
- `ipCidr`：支持单 IP 或 CIDR，例如 `123.146.0.21`、`127.0.0.1`、`192.168.1.0/24`
- `enabled`
- `remark`
- `createdAt`
- `updatedAt`
- `createdBy`
- `updatedBy`

可选扩展字段：
- `scopeType`：全局 / 指定账号 / 指定角色
- `scopeValue`
- `expiresAt`

## 接口建议

- `GET /api/admin/security/captcha-ip-allowlist`
- `POST /api/admin/security/captcha-ip-allowlist`
- `PUT /api/admin/security/captcha-ip-allowlist/{id}`
- `DELETE /api/admin/security/captcha-ip-allowlist/{id}`

权限建议：
- 仅 `ROLE_ADMIN`

## 登录判断逻辑建议

推荐逻辑：

```java
boolean skipCaptcha =
    captchaWhitelistEnabled
    && ipInWhitelist(clientIp)
    && accountAllowedForSkip(username, role);
```

建议不要只按 IP：
- 最好增加账号或角色范围限制
- 例如只允许 OpenClaw 学习账号、管理员测试账号使用

## 后端兜底配置

即使有管理页，也建议保留配置项：

```yaml
oms:
  security:
    captcha:
      whitelist-enabled: true
      whitelist-ips: 127.0.0.1,123.146.0.21
```

用途：
- 管理页出问题时可以应急恢复
- 数据库故障时仍可有静态兜底

## 审计建议

至少记录：
- 谁新增/修改/删除了白名单
- 修改前后内容
- 修改时间

登录命中白名单时，建议至少打日志：
- 用户名
- IP
- 是否跳过验证码

如果后续要更严谨，可以扩展专门的安全审计表。

## 风险控制建议

- 只信任受控代理转发的真实 IP
- 不要对白名单开放给所有公网账号
- 最好只对白名单 IP + 指定账号同时生效
- 可增加有效期，避免长期遗忘

## 最小可行实现（MVP）

第一阶段：
1. 后端配置白名单
2. 登录时按 IP 判断跳过验证码
3. 仅 admin 可查看命中日志

第二阶段：
1. 增加 admin 可维护页面
2. 白名单改为数据库存储
3. 增加审计日志和到期时间

这样最稳，也最方便逐步上线。
